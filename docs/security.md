# Security

How LeadBridge protects accounts, data and the extraction engine — and what you still have to do
on the infrastructure side.

---

## Authentication

- **Password hashing:** bcrypt (cost 12) via `bcrypt`. Plaintext passwords are never stored or
  logged.
- **Passwords:** at least `PASSWORD_MIN_LENGTH` characters (default 10) and must contain a letter
  and a number (`password_problems()` in `app/security.py`). Login does not reveal whether the
  e-mail or the password was wrong.
- **Sessions:** a signed JWT in an **httpOnly, SameSite=Lax cookie** (`leadbridge_session`),
  `Secure` when `COOKIE_SECURE=true`. The token is never placed in `localStorage`, never returned
  in a JSON body and never embedded in the SPA bundle.
- **Lockout:** `LOGIN_MAX_ATTEMPTS` failures (default 5) from one IP lock that IP out for
  `LOGIN_LOCKOUT_MINUTES` (default 15).
- **Logout** clears the cookie server-side; changing a password does not invalidate other
  sessions — shorten `ACCESS_TOKEN_EXPIRE_MINUTES` if you need that.
- **API keys** (`lbk_…`) are for machine clients (the extraction worker). Only a SHA-256 hash is
  stored; the plaintext is shown once at creation. Keys carry scopes, can be revoked, and every
  use updates `last_used_at` and is audited.

## Authorisation (RBAC)

Permissions are enforced **server-side on every request**, not by hiding buttons. The SPA hides
what a role cannot use, but the API is the authority.

| Permission | Admin | Manager | Agent |
| --- | :-: | :-: | :-: |
| `leads:read_all` | ✓ | ✓ | — (own + unassigned only) |
| `leads:write` | ✓ | ✓ | ✓ |
| `leads:assign` | ✓ | ✓ | — |
| `leads:verify` | ✓ | ✓ | — |
| `leads:delete` | ✓ | — | — |
| `sources:manage` | ✓ | ✓ | — (read-only) |
| `jobs:manage` | ✓ | ✓ | — |
| `imports:manage` | ✓ | ✓ | — |
| `exports:manage` | ✓ | ✓ | per org policy |
| `agents:manage` | ✓ | ✓ | — |
| `reports:read` | ✓ | ✓ | — |
| `audit:read` | ✓ | ✓ | — |
| `suppression:manage` | ✓ | ✓ | — |
| `settings:manage` | ✓ | — | — |
| `users:manage` | ✓ | — | — |
| `apikeys:manage` | ✓ | — | — |
| `backup:run`, `retention:manage` | ✓ | — | — |

Agent visibility: an agent sees only leads assigned to them or unassigned, and cannot read a lead
assigned to someone else (`403`). Exports for agents are automatically narrowed to their own leads
and refused entirely when `allow_agent_export` is off.

## Input handling

- All request bodies are validated by Pydantic models (lengths, enums, numeric ranges) before they
  reach the database.
- Phone/e-mail edits are re-parsed server-side; malformed values are rejected (`400`), not stored.
- Uploads: 12 MB and 20 000 row caps, MIME/extension checked, parsed with `csv`/`openpyxl` only
  (no formula evaluation, no macros). Imported spreadsheets never execute code.
- SQL is generated by SQLAlchemy with bound parameters — no string concatenation of user input.
- The SPA renders text as React text nodes; no `dangerouslySetInnerHTML`.

## Transport and headers

Middleware adds on every response:

```
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: geolocation=(), microphone=(), camera=()
Strict-Transport-Security: max-age=31536000; includeSubDomains   (production only)
Cache-Control: no-store                                          (all /api/ responses)
```

CORS is an allowlist (`CORS_ORIGINS`) with credentials enabled — never `*` with credentials.
Prefer same-origin deployment (the Vite proxy in development, Caddy/nginx or an edge Worker in
production) so CORS and cookie rules stay simple.

## Rate limiting

In-process sliding windows (`SlidingWindowLimiter`):

| Bucket | Default |
| --- | --- |
| Authenticated API calls per IP | 240/min |
| Sign-in attempts per IP | 12/min |
| Public lead-form submissions per IP | 20/min |

These are per process. Behind a CDN or with multiple instances, also apply limits at the edge
(Cloudflare rate limiting rules, nginx `limit_req` — both configured in `deploy/`).

## Audit trail

`ActivityLog` rows record actor, action, entity, IP, user agent and a JSON detail blob for:
sign-in/out, source create/update/enable/disable/delete/test, job start/pause/resume/stop,
lead update/verification/bulk actions/deletion, import and export, suppression changes, API key
creation/revocation and settings updates.

Per-lead `LeadAudit` rows record field-level changes (old value → new value), notes, verification
evidence, duplicate sightings and merges. Both are readable in the UI (Settings → Audit log, lead
drawer → timeline, CSV via Reports) and both respect retention windows.

## Secrets

- Adapter credentials live **only** in the API server's environment. A source stores the *name* of
  the variable (`credential_env`), never the value.
- The SPA receives permissions, status vocabularies and adapter metadata — nothing else. An
  automated test asserts the bootstrap payload contains no `secret`/`password` strings.
- `.env`, `*.db`, `backups/` and `node_modules/` are git-ignored. Never commit a real `.env`.
- Rotating `SECRET_KEY` invalidates all sessions (users must sign in again). Rotate after any
  suspected leak, and rotate API keys from Settings → API keys.

## Deletion and retention

- **Delete a lead** (`leads:delete`) removes the record, its duplicates and its audit rows, and by
  default writes the phone/e-mail to the suppression list so re-collection cannot resurrect it.
- **Do Not Contact** on a lead writes suppression entries automatically and flips consent to
  `denied`.
- **Retention purge** (Settings → Data & backups, or `cli.py purge-retention`) deletes leads older
  than `data_retention_days` (keeping converted/interested/DNC records) and audit rows older than
  `audit_retention_days`. Run it on a schedule and take a backup first.
- **Backups:** `POST /api/settings/backup` or `cli.py backup` produce a consistent SQLite snapshot
  (`VACUUM INTO`). Store copies off the server.

## What the crawler will not do

- No CAPTCHA solving, log-in bypass, paywall circumvention, header/IP spoofing to evade blocks, or
  retry storms against a refusing host.
- No collection from people-search sites, no personal/home data, no sensitive attributes
  (`PROHIBITED_FIELDS` are rejected at the API, adapter and import layer).
- `robots.txt` is fetched and honoured for every live request; the user agent identifies the bot
  and a compliance contact. Live collection requires an explicit per-domain allowlist.

## Hardening checklist for your deployment

- [ ] `ENVIRONMENT=production`, strong random `SECRET_KEY`, `COOKIE_SECURE=true`, HTTPS only.
- [ ] `SEED_DEMO_DATA=false`; demo accounts removed/changed; no shared logins.
- [ ] `ALLOWED_LIVE_DOMAINS` minimal and reviewed; `RESPECT_ROBOTS_TXT=true`.
- [ ] Reverse proxy sets `X-Forwarded-For`; the API is not exposed directly on the internet
      without TLS.
- [ ] Database file permissions 600 and owned by the service user; backups encrypted at rest.
- [ ] Logs shipped off-box and retained long enough to investigate an incident.
- [ ] Dependency updates applied (`pip install -U -r backend/requirements.txt`, `npm audit`).
- [ ] Separate accounts for each person, agents disabled when they leave.
- [ ] `grep -r "lbk_" frontend/dist` returns nothing (no keys in the bundle).
- [ ] A restore from backup has been *tested*, not just scheduled.

## Reporting a problem

If you find a vulnerability, open a private security advisory (GitHub → Security → Advisories) or
e-mail the maintainer rather than filing a public issue. Include reproduction steps and the
affected version (`/api/health` reports it).
